### Tool invocations behind the captured test outputs — annotation

The raw evidence files (`test1-*.txt` … `test6-*.txt`) are verbatim
`agentcore invoke` output. Since `agentcore invoke` prints only the agent's final
answer, each file ends with a section — `--- tool calls logged by the runtime
(CloudWatch) ---` — holding the tool invocations the agent runtime logged for that
turn, read straight from the runtime's CloudWatch log stream (the Strands agent
logs one `Tool #N: <name>` line per call). Nothing in those files was edited by
hand.

The capture window is the 90 seconds before each query, and the tests run back to
back, so a file can list a previous test's call as well; the last line is always
that test's own call.

Two Gateway targets are exercised, one of each integration type the rubric asks
for:

| Test | Tool invoked | Gateway target (integration) | Backing service |
|---|---|---|---|
| 1 — Order tracking | `order-tracker___get_order` | `order-tracker` (API Gateway REST proxy) | Lambda `order-tracker` |
| 2 — Refund | `order-tracker___get_order` then `refund-processor___initiate_refund` | `refund-processor` (direct Lambda) | Lambda `refund-processor` |
| 3 — Knowledge base | `search_knowledge_base` | — (local tool, Bedrock Retrieve API) | Bedrock Knowledge Base |
| 5 — Loyalty discount | `calculate_loyalty_discount` | — (local tool, Code Interpreter) | AgentCore Code Interpreter |
| 6 — Browser | `browser` | — (local tool) | AgentCore Browser |

Test 2 is the one that matters for the Gateway criterion: a single turn calls both
targets, the API-based one and the Lambda-based one.

**Why these responses prove the tools ran, not just that they were called**

- *Test 1.* The tracking number `TRK987654321`, the carrier `UPS` and the order
  line item (`Wireless Headphones Pro`, $89.99) live only in the `order-tracker`
  Lambda's order table (`starter/lambda/order_tracker.py`). They are not in the
  knowledge base — a search of `product_catalog.txt` for `ORD-001` or
  `TRK987654321` returns zero matches — and they are not in the model's training
  data. The delivery date is stronger still: the Lambda computes it at runtime as
  `now + 2 days`, so the date in the answer did not exist anywhere until the
  function ran. The agent has no other route to that data.
- *Test 2.* The refund identifier is generated at runtime inside the Lambda
  (`_new_refund_id()` returns `"REF-" +` eight random characters), so `REF-QJ8N3BW7`
  could not pre-exist anywhere. Its presence, together with the `APPROVED` status
  and the `3-5 business days` window, is proof that the Lambda-based Gateway target
  executed and returned a well-formed result.

Neither value appears in the agent's system prompt, the knowledge base, or any
static file, so both responses are tool-derived rather than generated.

**Well-formed results, not errors**

Both captured answers contain the fields the underlying service returned
(`status`, `carrier`, `tracking_number`, `estimated_delivery` for the order;
`refund_id`, `status`, processing window for the refund). Neither is an error
payload, a retry message, or an empty result.

**Independent protocol-level verification**

`evidence/mcp-gateway-verification.txt` captures the Gateway checked directly
over MCP, without the agent in the loop: the endpoint lists all six tools, and
`tools/call` is issued for both targets — `order-tracker___get_order` for ORD-001
(returns the tracking record) and `refund-processor___initiate_refund` for
ORD-002 (creates a refund in APPROVED state, `isError: false`). That confirms the
Gateway, its two targets and the Lambda backends independently of anything the
model did.
